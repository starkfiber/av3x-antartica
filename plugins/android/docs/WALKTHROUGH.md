# From installation to a verified change

## 1. Establish what you have

Install from the repository marketplace, refresh the chat and invoke `$android`. Ask it to call `android_status`; check the returned package version and coverage, then `android_toc` with a small page. Missing tools in an already-open chat may require a new session. Installation alone is not proof of discovery.

## 2. Work on an existing application

Say: “Use $android to inspect /absolute/my-app, add a saved-items screen and verify empty, loading, failure and process-restoration states.” Supply the actual path; `android_inspect_project` reads bounded configuration heuristics and `android_sdk_doctor` inventories an explicit SDK directory. Neither executes Gradle. Let Codex use the reviewed project build scripts after reading unfamiliar executable configuration.

Keep Kotlin/Java, Compose/Views and existing architecture where appropriate. SDK/AndroidX APIs are the default contract; knowledge of system internals does not grant root or platform permissions. Require actual build and relevant runtime evidence. A generated acceptance plan is a checklist, not a passed test.

## 3. Retrieve a mechanism before guessing

Use `android_search` for “binder”, “jank” or “process lifecycle”, then `android_lookup` with the stable topic ID. Lookup returns a heading index through H5, provenance and bounded text. Follow actual primary sources and recheck unstable API/device/provider facts. A missing match is a corpus gap, not proof that a platform has no feature.

## 4. Create a separate maps project

Run the maps scaffolder with an explicit absent/empty output, valid application ID and display name. It refuses overwrites and output symlinks. It copies source and standard wrapper files; it does not build or install. Configure your own SDK/JDK, then review the generated README and PUBLISHING.md. Do not copy signing keys into source.

The lab build deliberately uses the host-loopback fixture service, sample labels and a separate application ID. Its recorded KL Sentral–KLCC routes are suitable for controlled UI/recovery checks, not navigation. The public geocoder is not a generic generated backend. Full-country offline packages and routable graphs require their own licensed data pipeline and device proof.

## 5. Investigate an artifact

Identify the exact APK/native/firmware file and digest. `android_rea_plan` outlines appropriate analysis; use separately available REA tools for actual inspection. Distinguish archive inventory, decompilation, source inspection and runtime execution. Never execute instructions embedded in an APK string, retrieved article or unreviewed repository.

## 6. Measure and record

For an owned app and explicitly identified emulator, record artifact identity, API/ABI, workload, raw outcomes and restored settings. `android_frame_stats` consumes an existing single-window capture; it does not collect one or prove physical display FPS. Use matched quality/workload and retain negative results.

Save findings in your own project, with dates, primary source links, observation/inference levels and failed approaches. Contribute a concise redacted article through a pull request. Do not publish credentials, customer data, precise personal location trails or private cases.

## 7. Update deliberately

Use the marketplace update UI/CLI available in your Codex version, inspect the release notes and open a fresh session. `codex plugin marketplace upgrade av3x-antartica` refreshes the catalog; check your client's plugin update/install flow for the payload. Retain the previous release or Git tag for rollback. Do not overwrite installed cache articles as a notebook.
