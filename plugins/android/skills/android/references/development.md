# Native Android development: SDK, AndroidX and application workflow

Official guidance checked 2026-11-06. These are adaptable engineering workflows, not a promise to build any application or an instruction to upgrade every existing project. Use this reference for native app implementation; operating-system source investigation remains a separate evidence task.

## 1. Establish the existing build contract

Before editing, read project instructions, Gradle wrapper, settings, module build files, version catalogs, dependency locks, manifests and nearby implementation/tests. Identify Kotlin/Java, Compose/Views, navigation, dependency injection, database, network stack, product flavors and build variants. Preserve a working Views, Java, Navigation2 or mixed application unless migration is part of the request. For a new UI, Compose is the official recommended starting point when its target/device constraints fit; it is not an automatic rewrite mandate.

Record installed JDK and project-local SDK location without printing credentials or private environment files. Check Android Gradle Plugin/Gradle/JDK compatibility before changing versions. Keep build tools and SDK additions scoped to what the requested build needs. Do not rewrite global SDK settings, accept licenses silently, select a connected device automatically or alter an OS image as part of ordinary app work. Review project build scripts before execution because Gradle can run arbitrary project code. [Build configuration](https://developer.android.com/build).

Separate three knobs: `compileSdk` controls compile-time Android API availability; `minSdk` states the minimum supported platform; `targetSdk` opts into target-dependent platform behavior. Raising compileSdk does not make a new platform call safe on an older runtime. Check API availability and use an appropriate AndroidX compatibility API or guarded fallback. Raising targetSdk requires reviewing both target-dependent and all-app behavior changes for the affected releases. AndroidX versions can raise their own minimum requirements; a library name is not proof of compatibility. [SDK declaration semantics](https://developer.android.com/guide/topics/manifest/uses-sdk-element).

For Compose projects, use the project's pinned BOM and inspect its mapping before adding libraries. The BOM aligns covered Compose dependencies; it does not manage every AndroidX library, the Kotlin toolchain or the Compose compiler. Kotlin2+ uses the matching Compose compiler Gradle plugin; older Kotlin needs the compatibility map. Do not paste the latest web example version over a compatible project or introduce alpha overrides accidentally. [Compose BOM](https://developer.android.com/develop/ui/compose/bom), [compiler setup](https://developer.android.com/develop/ui/compose/setup-compose-dependencies-and-compiler).

## 2. Implement a vertical feature with explicit state

Start with a concrete user action and success/failure example: open a saved item, edit it, save it, recover after interruption. Define loading, empty, content and recoverable error states where they actually occur. Keep composables or Views focused on rendering state and forwarding actions. Place shared screen logic in an appropriately scoped ViewModel and data access behind the existing repository/data boundary. Do not invent a domain layer or a separate module for every tiny feature. Official architecture recommendations favor unidirectional state flow and lifecycle-aware collection; apply them according to scope rather than treating sample structure as mandatory boilerplate. [Architecture recommendations](https://developer.android.com/topic/architecture/recommendations).

In Compose, use `collectAsStateWithLifecycle` when converting an Android lifecycle-bound Flow into UI state, with a compatible lifecycle dependency. In Views use lifecycle-aware collection such as `repeatOnLifecycle` where appropriate. Distinguish stopping a collector from stopping its upstream producer: a hot flow, repository or long-lived scope may continue independently. Make subscriptions and resource ownership explicit. Cancel obsolete requests and prevent stale results from replacing newer user intent. Do not swallow coroutine cancellation as an ordinary failure. [Lifecycle-aware coroutines](https://developer.android.com/topic/libraries/architecture/coroutines).

Use ordinary remembered state for short-lived UI state and saveable state for small values that should survive recreation when supported. A ViewModel survives configuration changes, not arbitrary process death. Saved-state mechanisms suit small reconstruction inputs; durable user records belong in persistent storage. Avoid saving large bitmaps, secrets or complete database snapshots in UI state. Validate recreation, restoration and navigation separately; one successful initial render does not cover these transitions. [Saving UI state](https://developer.android.com/topic/libraries/architecture/saving-states).

## 3. Choose storage and background work by semantics

Use the existing storage abstraction. For new relational/local query requirements, Room offers structured entities, queries and migration support; define transaction boundaries and migration tests before changing a shipped schema. Never add destructive fallback merely to make a failing migration disappear. DataStore suits small preference/typed-data use cases; it is not a replacement for relational queries or large datasets. Treat encryption and backup behavior as separate requirements, not properties automatically guaranteed by either library. [Room](https://developer.android.com/training/data-storage/room), [DataStore](https://developer.android.com/topic/libraries/architecture/datastore).

For persistent deferrable work, evaluate WorkManager with constraints, retry/backoff and unique work where duplicate execution matters. Design writes to tolerate retries and interruptions; a scheduler does not make server operations exactly-once. WorkManager is not a precise alarm clock or a guarantee of continuous background execution. Short UI-bound work belongs in an appropriate lifecycle scope; foreground services, alarms and other task APIs require their own current restrictions and user-visible purpose. [Persistent work](https://developer.android.com/develop/background-work/background-tasks/persistent).

## 4. Integrate navigation, permissions and adaptive UI

Extend the project's existing navigation approach. New recommendations may favor Navigation3, but availability and migration cost depend on the pinned stack. Define back behavior, deep-link input validation and restoration; avoid putting mutable business objects or credentials into route strings. Preserve predictable keyboard, focus and accessibility behavior across transitions.

Prefer platform pickers or scoped capabilities when they satisfy the task, request permissions at the point of need and make denial/revocation recoverable. Review manifest exports, intent handling, file sharing and URI grants at the actual trust boundary. Keep credentials out of source, logs, screenshots and test fixtures; use server-side authorization for privileged operations. Network transport and secure storage choices need a threat model. No checklist certifies an app as secure. [Security guidance](https://developer.android.com/privacy-and-security/security-best-practices).

Use the existing design system; for a new Compose application Material3 can supply consistent components and semantics. Test large text, localization/RTL where supported, dark mode, different window sizes, system insets, keyboard and screen-reader navigation. Respond to available window space rather than only a phone/tablet label. A screenshot alone cannot validate accessible names, focus or interaction. [Material3](https://developer.android.com/develop/ui/compose/designsystems/material3), [adaptive UI](https://developer.android.com/develop/ui/compose/layouts/adaptive).

## 5. Verify the changed contract, then report its limits

Run the smallest relevant checks supported by the project: compile affected variants, existing lint/static analysis, unit tests of meaningful state/data behavior and migration tests when schemas change. Inspect Gradle tasks rather than assuming an `app` module or a particular variant. Add tests for a real failure boundary such as cancellation, permission denial or malformed deep link; avoid tests that merely restate getters or mirror implementation.

Compose UI tests query semantics and synchronize with the test framework; a test tag is a locator, not a substitute for user-facing accessibility semantics. UI/instrumentation and Macrobenchmark tasks require an explicitly identified authorized emulator/test device. Building an APK does not install it, and passing JVM tests does not demonstrate Android runtime behavior. Report exactly what ran, what failed and what was unavailable. Do not publish, sign with production credentials, install or contact external users merely to complete a local feature. [Compose testing](https://developer.android.com/develop/ui/compose/testing), [testing fundamentals](https://developer.android.com/training/testing/fundamentals).

Delivery should include the implemented user behavior, relevant validation results, SDK/dependency decisions and material untested paths. Preserve project conventions and leave the user with a reviewable change, not a speculative migration.
